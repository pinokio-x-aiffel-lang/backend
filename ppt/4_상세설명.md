# 4단계 — KOSIS 후보 통계표 검색 (Retrieve KOSIS Candidates)

> 코드: `src/modules/retrieve_kosis_candidates.py` · 키워드 확장: `src/kosis/keyword_expand.py`
> 검색 API: `src/kosis/search.py`(`search_tables_many`, `statisticsSearch.do`)
> 프롬프트: `EXPAND_KEYWORDS_*` (`src/prompts/prompts.py`)
> 파이프라인 등록명: **"KOSIS 통계표 n개 찾기"** (`src/pipeline/runner.py`, step 4)

---

## 1. 한 줄 정의

> **각 claim의 주제(subject)를 가지고 KOSIS(국가통계포털)에서 검증에 쓸 통계표 후보 상위 10개를 찾아오는 단계.**

3단계까지는 claim 내부 정보만 다뤘다. 4단계부터 **외부 실측 데이터(KOSIS)**와 연결된다.
이 단계는 "어느 통계표를 봐야 이 주장을 검증할 수 있나?"를 푼다. 단, **단 하나로 확정하지 않고** 후보 풀(최대 10개)만 만든다 — 최종 1개 선정은 5~6단계의 몫.

---

## 2. 파이프라인 안에서의 위치

| 구분 | 내용 |
|---|---|
| **입력** | `master_schema.claims[*]` (특히 `subject`, `unit`, `period`) |
| **출력** | `master_schema.analysis` : claim별 `ClaimAnalysis` 리스트 |
| └ `kosis_search` | 통합검색 로그 (사용한 키워드 변형, 히트 수, 임시 선정표) |
| └ `candidates` | 병합·재랭킹 후 **상위 10개** 후보 통계표(`KosisCandidate`) |
| └ `kosis_query` | placeholder — **5단계에서 채움** |
| **처리 단위** | 모든 claim **병렬**(`asyncio.gather`) |
| **실패 격리** | 한 claim 검색 실패(`KosisError`/`ValueError`)는 `success=0`으로 기록하고 **계속 진행** |

> 정확한 통계표 1개 선정은 이후 단계 몫이라, 일단 **RANK 1위만 임시 selected**로 둬서 5단계가 동작하게 한다.

## 3. 핵심 설계 — "여러 검색어 변형으로 recall 끌어올리기"

KOSIS 검색은 통계표명에 쓰인 어휘와 정확히 맞아야 잘 걸린다. 그런데 기사 subject(`"청년층 고용률"`)와 통계표명(`"고용률"`)은 표현이 다르다. → **하나의 키워드가 아니라 여러 변형으로 검색해 합친다.**

```
claim.subject
   │
   ├─① 키워드 변형 생성 (expand_subject, 결정적 룰)
   │     변형[0]=베이스라인, +괄호/수량어 제거, +수식어 분리, +동의어 치환
   │     (최대 MAX_VARIANTS=4개)
   │
   ├─② 다중 검색 (search_tables_many → statisticsSearch.do)
   │     변형별로 KOSIS 통합검색, 각 top_n
   │
   ├─③ 병합·dedup (_merge_dedup)
   │     변형 순서대로 union, tbl_id 기준 중복 제거(첫 등장 유지)
   │
   ├─④ 재랭킹 (_rerank_hits)
   │     시군구통계·국제통계를 후순위로 → 상위 TOP_N=10개 절단
   │
   └─⑤ (룰 검색 0건일 때만) LLM 폴백 재검색
         expand_keywords(HCX-007)로 검색어 보강 → 재검색
```

---

## 4. ① 키워드 변형 생성 (`expand_subject`, 결정적 룰)

subject 하나에서 `{원본 · 핵심명사 · 동의어 · 상위어}` 변형을 만든다. 전부 결정적이라 재현 가능.
**변형[0]은 기존 전처리 키워드** — 확장이 비어도 베이스라인과 동일하게 동작.

| 변형 종류 | 처리 | 예시 |
|---|---|---|
| **[0] 베이스라인** | 국가 한정어 제거 + 공백 제거 | `"한국의 경제성장률"` → `"경제성장률"` |
| **노이즈 제거** | 괄호 `(…)`, 수량·단위(`10개`,`1인당`), `평균` 제거 | `"쌀 소비량(1인당)"` → `"쌀 소비량"` |
| **선행 수식어 분리** | 인구집단 수식어(청년층·고령 등) 떼기 | `"청년층 고용률"` → `"고용률"` |
| **동의어·상위어 치환** | KOSIS 어휘로 치환 | `"집값"` → `"주택가격"`, `"물가"` → `"소비자물가지수"` |

선행 수식어 후보: `청년층·청년·고령자·고령·노인·전체·국내·국민·15~29세·20대~60대` 등
동의어 사전(일부): `쌀→양곡`, `가계신용→가계부채`, `집값→주택가격/주택매매가격`, `물가→소비자물가지수`, `근로자→취업자`, `임금→근로소득/임금근로`, `소매판매→소매판매액지수`, `출생아→출생`, `자살률→고의적 자해/자살`.

> 호출 증폭 방지: subject당 변형은 **최대 4개**(`MAX_VARIANTS`)로 절단 → KOSIS 호출 폭증 가드.

---

## 5. ②③④ 검색 → 병합 → 재랭킹

### ② 다중 검색 (`search_tables_many`)
- KOSIS 통합검색 API `statisticsSearch.do` 를 변형별로 호출(`sort=RANK`, 각 `top_n=10`).
- 결과는 `SearchHit`(통계표 1건): `org_id · tbl_id · tbl_nm(표명) · org_nm(기관) · stat_nm(조사명) · prd_de(수록기간)`.
- ⚡ **변형 검색은 병렬**(`ThreadPoolExecutor`) — 변형 4개를 동시에 쏜다(과거엔 순차 for-loop; `perf(kosis): parallelize multi-keyword search`로 변경). 공유 client rate limiter가 ≤1000/min을 강제해 **트래픽 폭증은 없고**, claim당 검색 지연만 ~4× 단축. 한 변형 실패(`KosisError`)는 흡수해 빈 리스트로 두고 나머지는 보존.

### ③ 병합·dedup (`_merge_dedup`)
- 변형 순서대로 결과를 union, **`tbl_id` 기준 중복 제거**(먼저 등장한 것 유지).

### ④ 재랭킹 (`_rerank_hits`) — 왜 필요한가

| 표 종류 | 점수(낮을수록 우선) |
|---|:---:|
| 일반 통계표 | 0 (우선) |
| 국제통계 (`tbl_id`가 `DT_2*`) | 1 (후순위) |
| 시군구통계 (`stat_nm`=="시군구통계") | 2 (최후순위) |

> **전국(계) 표가 시군구·국제표에 밀려 TOP_N 밖으로 잘리는 것을 막는다.**
> 오버페치한 뒤 stable sort로 일반표를 앞으로 당기고 **상위 10개만** 후보로 남긴다.

---

## 6. ⑤ LLM 폴백 — "진짜 미스"일 때만

룰 변형 검색 결과가 **0건일 때만**(=진짜 검색 미스) LLM으로 검색어를 보강해 재검색한다.
→ LLM 호출·비결정성·KOSIS 호출을 **최소화**하는 설계.

- 모델: `HCX-007`, max_tokens 128, temperature 0, Structured Outputs(JSON 배열) 강제.
- 프롬프트 규칙:
  - KOSIS 통계표명에 쓰일 어휘로 동의어·상위어·핵심명사 제시 (예: `"1인당 쌀 소비량"` → `["양곡소비량","쌀 소비량","1인당 양곡소비량"]`)
  - **가격·시세·매출·해외지표 등 KOSIS에 없을 주제는 빈 목록** 반환 (지어내기 금지)
  - 최대 4개.
- 폴백 검색어는 기존 변형과 중복 제거 후 최대 4개만 재검색.

## 8. 사용 모델·파라미터·상수

| 항목 | 값 |
|---|---|
| 후보 상한 `TOP_N` | 10 (병합·재랭킹 후 절단) |
| subject당 변형 상한 `MAX_VARIANTS` | 4 |
| 검색 API | `statisticsSearch.do`, `sort=RANK` |
| LLM 폴백 모델 | `HCX-007`, max_tokens 128, temp 0 |
| 키워드 변형 생성 | **LLM 없음** — 결정적 룰(`expand_subject`) |
| 검색 동시성 | claim 간 `gather` + **키워드 변형 간 `ThreadPoolExecutor`(병렬)** |

> KOSIS 호출은 직접 구현(MCP 미사용). 동시성: **claim 간 `gather` + 키워드 변형 간 `ThreadPoolExecutor`**. rate limit 1000/min은 공유 client가 sliding-window lock으로 강제 → 동시 발사해도 한도 초과 불가(폭증 없음).

## 9. 성능 (벤치마크 `benchmark/4_retrieve/leeaain_260619_01.md`)

**값-기반 Recall** — 검색한 후보표 중 하나라도 정답 figure 값을 실제로 담고 있는지 KOSIS raw로 확인.
(정답 '표 라벨링' 없이 figure 값(SSOT, 독립)만으로 측정 → 비순환)

| 지표 | 값 | 95% CI |
|---|---|---|
| Recall@1 | 0.128 (29/226) | [0.091, 0.178] |
| Recall@3 | 0.279 (63/226) | [0.224, 0.341] |
| **Recall@10** | **0.350** (79/226) | [0.290, 0.414] |
| MRR | 0.210 | — |
| 검색 실패율 | 0.013 (3/226) | [0.005, 0.038] |

**Recall@N 읽는 법:** @뒤 숫자 = 상위 몇 개 후보까지 보는가. @1=1순위에 정답, @10=상위 10개 안에 정답.

**해석**
- 값-기반 Recall은 "검색이 값이 든 표를 가져왔나"를 본다(정본명 일치보다 시스템 목적에 부합).
- **델타(증감) figure는 단일 셀에 값이 없어 자연히 미검출** → 검색 탓이 아닌 정직한 결과.
- 이 단계가 **전체 파이프라인의 주요 병목** — recall이 낮으면 하류가 아무리 정확해도 검증 불가(NEI)로 빠진다. itmId 결정적 매칭(LLM 폴백 부재)이 원인으로 식별됨.

## 10. 한 줄 정리

> 4단계는 **"claim 주제 → KOSIS 통계표 후보 10개"** 검색기다.
> 핵심은 ① **결정적 키워드 변형 다중 검색 + 병합/재랭킹**(recall↑), ② **진짜 미스일 때만 LLM 폴백**(비용·비결정성 최소화),
> ③ **확정이 아닌 후보 풀** 생성(선정은 5~6단계)이며, 외부 실측과 연결되는 첫 관문이자 파이프라인 recall의 핵심 병목이다.
