# DART 계정 사전 정책

## 매칭 원칙
- XBRL `account_id` **우선** 매칭, 라벨 별칭은 보조(감사보고서 원문 경로용).
- **실데이터로 검증한 것만** 등록 — account_id 추측 금지.
- 매칭된 id/라벨은 `DartFact`에 기록(출처 추적용).

## 검증된 seed (`src/dart/accounts.py`)
| 개념 | account_id | 라벨 변형 |
|---|---|---|
| 매출 | `ifrs-full_Revenue` | 매출액 / 영업수익 |
| 영업이익 | `dart_OperatingIncomeLoss` | 영업이익 / 영업이익(손실) |
| 당기순이익 | `ifrs-full_ProfitLoss` | 당기순이익 / 당기순이익(손실) |
| 이자수익(금융) | `ifrs-full_RevenueFromInterest` | 이자수익 |
| 수수료수익(금융) | `ifrs-full_FeeAndCommissionIncome` | 수수료수익 |

> **금융사 주의:** 은행·금융지주는 단일 '매출/영업수익' 표준계정이 **없다**(수익이 이자·수수료·보험 등으로 분해). `매출`에 섞지 말고 위 구성요소로 질의 — 클레임의 '매출'이 어느 항목인지는 상류 LLM 라우팅이 특정.

## 확장 정책: miss → log → add
모든 업종을 미리 망라하지 않는다. **가짜뉴스 클레임에 실제 등장하는 업종부터.**

1. 매칭 실패(`None`) 발생 → **로깅**.
2. 해당 기업 원본에서 실제 account_id **확인**.
3. 검증된 id/별칭을 `_CONCEPTS`에 **한 줄 추가**.

업종별 변형(예: 금융사 매출 = `영업수익`, 다른 표준ID)도 이 루프로 흡수한다.
거대한 추측 사전보다 **점진 확장**이 낫다.

## 비고
- 단위 배율은 코드가 결정적으로 처리(원문 `단위: 백만원` 등을 읽어 곱함). LLM 판단 아님.
- 구조화 API(`fnlttSinglAcntAll`)는 항상 원 단위. 단위/파싱 이슈는 감사보고서 원문 경로 한정.
