### 2-4. MCP `get_table_metadata` 한계 발견

**30건 전체에서 `dimension_count: 0`, `item_count: 0` 반환.**

```json
{
  "structure": {
    "dimensions": [],
    "dimension_count": 0,
    "items": [],
    "item_count": 0
  }
}
```

MCP의 metadata 엔드포인트는 표의 **축(분류항목) 구조와 세부 항목 목록을 반환하지 않는다**. 실제 ITM/PRD/ORG 구조는 KOSIS raw API(`getMeta`)를 직접 호출해야 확인 가능하다. 또한 `org_nm`도 빈 값으로 반환된다.

## 3. 주목할 케이스 상세 분석

### Case 1 — 단순 단일 지표 (easy)

**`DT_2KAAD31` 교통사고 사망자 수**

```json
{
  "table_info": {
    "tbl_id": "DT_2KAAD31",
    "tbl_nm": "교통사고 사망자 수",
    "org_id": "101",
    "org_nm": "",
    "prd_se": "Y",
    "period_range": "1994~2025"
  },
  "structure": {
    "dimensions": [],
    "dimension_count": 0,
    "items": [],
    "item_count": 0
  },
  "suggested_query": {
    "example": "get_statistics_data('101', 'DT_2KAAD31', '1994', '2025')"
  }
}
```

표명이 곧 지표명. "교통사고 사망자"라는 키워드가 나오면 직접 매칭 가능한 **easy 케이스**. 30년 연간 시계열.

---

### Case 2 — 동일 지표 중복 표 (주기 다름)

**`DT_2IFS002` vs `DT_2OEEO0121` 소비자물가지수**

```json
// 표 1: 월간
{
  "tbl_id": "DT_2IFS002",
  "tbl_nm": "소비자물가지수",
  "prd_se": "M",
  "period_range": "1960.01~2026.04"
}

// 표 2: 분기 (OECD 기준)
{
  "tbl_id": "DT_2OEEO0121",
  "tbl_nm": "소비자물가지수",
  "prd_se": "Q",
  "period_range": "1960 1/4~2027 4/4"
}
```

표명이 동일하지만 주기(월간 vs 분기)와 출처(국내 vs OECD)가 다르다. 임베딩 검색에서 두 표가 동시에 top-K에 올라올 가능성이 높다. **올바른 표 선택은 claim의 시점 표현 방식과 출처 언급으로 결정**해야 한다.

### Case 3 — 고차원 복합 표 (hard)

**`DT_1B34E07` 사망원인(237항목)/성/연령(5세)별 사망자수, 사망률**

```json
{
  "tbl_id": "DT_1B34E07",
  "tbl_nm": "사망원인(237항목)/성/연령(5세)별 사망자수, 사망률",
  "org_id": "101",
  "prd_se": "Y",
  "period_range": "1983~2024"
}
```

표명에서 구조가 드러난다: **사망원인 237가지 × 성별 × 연령(5세 단위) × 사망자수/사망률**. 실제 셀 수는 수십만 개 규모. "암 사망률"처럼 특정 사망원인을 언급하는 claim이면 이 표로 연결되지만, 어느 ITM_ID를 써야 하는지 결정하는 것은 별도 로직이 필요한 **hard 케이스**.

## 4. 임베딩 검색 설계를 위한 인사이트

### 발견 1 — 동일 지표 중복 표 문제
같은 표명을 가진 표가 주기(Y/M/Q)나 출처(국내/OECD)만 다르게 여러 개 존재한다. top-K 검색 결과에서 중복 후보가 다수 나올 수 있으므로, **coarse 검색 후 claim의 주기·출처 정보로 fine 필터링**하는 2단계가 필요하다.

### 발견 2 — 표명에 구조 힌트가 있다
`사망원인(237항목)/성/연령(5세)별`처럼 표명 자체에 축 구조가 서술형으로 포함된 경우가 있다. 임베딩 입력에 표명만이 아니라 **ITM 항목명까지 포함**하면 세부 축 매칭 정확도가 올라갈 것으로 예상된다.

### 발견 3 — 미래 추계값과 실측값 혼재
기간이 현재 이후까지 포함된 표는 추계값을 담고 있다. Claim 검증 시 **해당 연도가 추계 구간인지 아닌지를 체크**하는 로직이 필요하다.

### 발견 4 — 단년도 표 다수 존재
특정 조사가 1회성 또는 격년제인 경우, 기간 커버리지가 매우 짧다. 표가 매칭되더라도 claim 연도의 데이터가 없을 수 있으므로, 검색 결과에 **기간 범위 일치 여부를 함께 표시**하는 것이 좋다.

### 발견 5 — MCP metadata API는 구조 정보를 반환하지 않음
`get_table_metadata`의 `dimensions`, `items`가 모두 빈 배열로 반환된다. 실제 ITM/PRD 축 구조 확인은 KOSIS raw API(`getMeta`) 직접 호출이 필요하다. 임베딩 인덱스 구축 시에는 **이미 크롤링된 `kosis_meta_final.csv`의 embedText 컬럼**을 사용하는 것이 현실적이다.

## 5. 참고: 실제 ITM 구조 예시 (raw API 결과)

MCP metadata 대신 raw API로 확인한 `DT_MOGE_1540002657`(학교폭력 피해 신고 도움 정도)의 실제 구조:

```
축 A — 특성별 (응답자 분류)
  ├── 전체
  ├── 성별: 남자, 여자
  ├── 남녀공학별: 남학교, 여학교, 남녀공학
  ├── 학교급별: 초등, 중학교, 고등학교
  ├── 학년별: 초4 ~ 고3 (9단계)
  └── 지역별: 17개 시도

축 B — 도움정도별 (설문 응답)
  ├── 문제를 완전히 해결하는데 큰 도움이 됨 (%)
  ├── 어느 정도 도움 됨 (%)
  ├── 도움이 되지 않았으나 추가 피해도 없음 (%)
  └── 문제가 해결되지 않고 더 피해를 봄 (%)
```

이처럼 설문 기반 표는 특성별 × 응답별 2축 구조가 일반적이다.
